# コーディングルール

この文書はRust Core、Python Analysis Service、C# / Avalonia GUIで共通して使う設計・実装規則を定める。言語固有の書式やAPI利用方法は、各ツール設定と対象機能の仕様に従う。

`必須`は満たす必要がある規則、`基本`は採用を推奨する規則を示す。基本から外れる場合は、既存契約や安全性を損なわない理由を説明できるようにする。

## 1. オブジェクトとmessage

- **必須:** オブジェクトは自身の状態と不変条件を所有する。呼び出し側から内部状態を直接書き換えさせず、公開した操作を通じて変更する。
- **必須:** 公開操作は利用者の意図を表す名前にし、入力・成功時の結果・失敗を呼び出し側が判別できる形で返す。失敗を無視したり、正常値に見える値へ置き換えたりしない。
- **基本:** 1つの型やモジュールへ無関係な責務を集めない。状態遷移、外部I/O、画面表示など変更理由が異なる処理は、必要に応じて分割する。
- **基本:** interfaceは外部依存の置換、複数実装の共通契約、テスト境界など、役割が明確な場所に定義する。すべての型にinterfaceを追加しない。
- **基本:** interface継承は、派生interfaceが親の契約を満たすときに使う。アクセス制御は内部状態と実装詳細を隠すために使う。継承の階層を増やすこと自体を目標にしない。

ここでいうmessageは、オブジェクトの公開操作やAPI上の要求など、受け手と契約が明確な依頼を指す。すべての操作を専用messageクラス、非同期キュー、ブローカーへ変換する規則ではない。

## 2. UI / Process / Dataの責務

責務を論理的に分け、担当の境界を越えるときは公開APIまたは型付き契約を使う。3分類をディレクトリ、クラス、実行プロセスへ機械的に一対一対応させない。

| 責務 | 担当すること | 避けること |
|---|---|---|
| UI | 入力受付、表示、画面状態への変換。Rust Core APIの呼び出し | Song Dataの直接保存、Python解析の直接起動、音声処理 |
| Process | ユースケース、処理順序、Job状態と失敗の管理。Rust CoreやPython Analysisの処理 | UI固有の画面型・表示方法への依存 |
| Data | Song Data、設定、解析生成物の保存・読込と形式検証 | 画面表示やユースケースの判断 |

このプロジェクトの基本経路は`GUI → Rust Core API → Python Analysis API`である。Song Dataの正本とJob管理はRust Coreの契約に従い、解析サービスとの入力・結果・生成物の受け渡しも契約で明示する。UIから保存先や解析モデルへ直接到達する経路を追加しない。

## 3. 境界とエラー

- **必須:** 外部から入る値は、所有する境界で形式・範囲・単位を検証する。内部関数では確立済みの型や不変条件を利用し、同じ検証を理由なく繰り返さない。
- **必須:** APIや保存形式の変更では、利用側、互換性、バージョン、移行方法を確認する。境界データに暗黙の単位や時刻基準を持ち込まない。
- **必須:** エラーには処理段階と回復に必要な情報を含め、Job/APIの契約に従って呼び出し元へ返す。例外を握りつぶしたり、別の層の表示文言へ変換して内部契約に混ぜたりしない。
- **基本:** モデルや外部ツールはAdapter越しの契約で呼び出し、モデル固有形式を他の層へ漏らさない。
- **必須:** 内部音声時刻は48 kHz基準の整数sample indexを使う。秒やモデル固有の時刻形式との変換は境界で行う。
- **必須:** リアルタイム音声callbackへPython、モデル推論、ファイルI/Oなど時間の読めない処理を持ち込まない。

## 4. テストと検証

- **必須:** 変更した実装単位に対応するテストまたはEvaluatorを用意し、公開message/APIの入力、結果、失敗時の契約を確認する。
- **基本:** Jobやサービスの状態を変える処理では、正常遷移に加えて不正入力、失敗、キャンセル、重複要求など該当する境界ケースを確認する。
- **必須:** mockや合成fixtureの成功は、そのmock契約やアルゴリズムの検証結果として扱う。実モデル、実録音、GUI、配布物で未確認の挙動まで確認済みと報告しない。
- **必須:** 失敗、skip、未実行、実行中、確認できない範囲を成功と区別する。

## 5. ソースコードコメント

[JSON-like Comment Outs](https://github.com/tomiya7688/Json-like-comment-outs)を宣言レベルのコメント規則として採用する。参照仕様はDraft v0.9のため、人間が読みやすいことを優先し、ツール解析上の推奨を独自の必須規則へ強めない。

### 宣言コメント

- **必須:** クラス、関数、メソッドの宣言に、責務と契約を説明するコメントを付ける。Rustでは型・関数・メソッド、C#では型・メソッド、Pythonではクラス・関数・メソッドなど、各言語の対応する宣言単位に適用する。
- **必須:** クラスや状態を持つ型には`責務`と`フィールド`を記載する。`フィールド`には主要な状態だけを書き、状態を持たない型では空のリストを使う。
- **必須:** 関数・メソッドには`責務`、`処理`、`引数`、`戻り値`を記載する。引数や戻り値がない場合も空のリストで示す。`処理`は意味のある段階を実際の順序で並べる。
- **基本:** 項目名と説明には読み手に自然な言語を使う。このリポジトリでは日本語キーと説明を標準とし、既存の英語規約がある範囲では英語に揃える。同じブロック内で同じ意味の日本語キーと英語キーを混在させない。
- **基本:** 引数・フィールド名はソース上の名前と対応させる。`副作用`、`エラー`、`補足`は読み手に必要な場合だけ追加し、空の任意項目を機械的に埋めない。

### 書式

各言語で宣言に付随する標準の記法を使う。RustとC#では`///`形式のドキュメントコメント、C#でXML文書コメントを生成する場合はプロジェクト既定のXML要素、Pythonではクラス・関数・メソッドのdocstringを使う。コメント本体は次の形を基本とする。

```text
{
  責務: [
    CreateAnalysisJob: 解析ジョブを登録する
  ]
  処理: [
    1: 入力契約を検証する
    2: 解析ジョブを登録する
  ]
  引数: [
    request: 解析対象と設定
  ]
  戻り値: [
    jobId: 作成した解析ジョブの識別子
  ]
  副作用: [
    Job状態を保存する
  ]
  エラー: [
    invalid_request: 入力契約を満たさない
  ]
}
```

この書式はJSON風のコメントであり、有効なJSONへ変換する必要はない。トップレベル項目の順序や引用符・カンマを強制せず、深い入れ子を避ける。`処理`内の番号付き順序には実行順の意味を持たせる。

### 実装内部のコメント

関数・メソッド内部、条件分岐、変数、処理単位には通常の短いコメントを使う。コードの言い換えより、理由、意図、非自明な値や状態の意味を書く。内部の各行をJSON-like形式で説明しない。

### 保守

コメントの責務、処理、フィールド、引数、戻り値は実装と一致させる。宣言名、処理順、状態、入出力の意味を変えたときは対応するコメントも更新する。自動解析との互換性より、読み手が理解しやすい表現を優先する。

詳細は[日本語仕様](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/SPECIFICATION.md)と[テンプレート](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/TEMPLATE.md)を参照する。

## 6. 変更単位

Issueから選んだ実装単位のGoal、Acceptance、source、対応テスト、依存関係を確認してから変更する。無関係なリファクタリングを混ぜず、仕様・共有契約・テスト・必要な文書を一緒に更新する。Issue分割、優先度、P0の扱いは[実装計画](implementation_plan.md)に従う。

## 実装時の確認

変更のレビューでは、次を確認する。

1. 公開操作の責務、入力、結果、失敗が明確か。
2. 状態と不変条件を担当オブジェクトが所有しているか。
3. UI / Process / Dataの境界を飛び越える依存がないか。
4. 時刻、保存形式、モデル固有データなどの契約を境界で扱っているか。
5. 宣言コメントが規則に沿い、実装と一致しているか。内部コメントをJSON-like形式にしていないか。
6. 対応テストが成功・失敗の振る舞いを確かめ、未検証範囲も区別できているか。

設計背景は[アーキテクチャ](architecture.md)を参照する。Smalltalk型message-oriented設計とUPDの責務分離を採用する意図は同文書に記録し、Commander / Messengerの専用構造は要求しない。

## 継承の共通規約（必須・レビュー基準）

### 禁止条件
- **具象クラスAを継承するクラスBを、Cがさらに継承することを禁止する。** `具象A → B → C`はBが抽象・具象のどちらでも違反。
- **`抽象A → 具象B → C`は、この禁止には該当しない。** ただし自動的に設計が承認されるわけではない。`具象B → C → D`まで伸びれば禁止。
- `具象A → B`自体は一律禁止せず、既存のより厳しい規約があればそちらを優先する。暗黙の`Object`等の最上位基底型とインターフェースは、この判定から除外する。

### 継承する意味と読みやすさ
- **具体的な処理を持つクラスの継承は原則避け、継承自体に意味がないなら委譲・合成を優先する。** 抽象クラスに実装済み処理がある場合も検討対象。
- 具象・抽象を問わず、意味のある共通の形・契約が既にある、または同じ形が合理的に必要になると予想できるときだけ継承を検討する。無意味な抽象階層を将来のためだけに増やさない。
- 禁止規則に違反しなくても、読みにくい、責務や置換可能性が曖昧、変更の波及が過大な継承は**レビューで不合格**とする。

### 例外・適用範囲
- 意図的な多段継承が設計正本に理由・範囲とともに明記された箇所だけ例外とする。既存実装の存在のみでは例外にならない。
- コンパイラ・静的解析器が扱う入力例、検証fixture、教材のコード例は本番実装規約と区別する。
- 新規・変更するプロジェクト所有コードに適用。無関係な既存コードの一括修正は要求しない。
