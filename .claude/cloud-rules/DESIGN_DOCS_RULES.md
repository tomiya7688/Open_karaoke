# 設計書ルール（エージェント・人間共通）

正本は日本語。英語版は任意の翻訳（`docs/en/`、食い違えば日本語が優先）。根拠の調査: Diátaxis、arc42、C4、MADR、Google文書ガイド、Docs as Code、JTFスタイルガイド（2026-11-06にCodex gpt-6-lunaで調査）。

## 構成

1. 入口は `docs/README.md`（目次）1つだけ。`AGENTS.md`・`CLAUDE.md` はここへのリンクだけにする。テンプレート: `INDEX_TEMPLATE.md`。
2. 目次には「このページの使い方」「正本と更新ルール」「全体設計」「機能別設計の表（機能・何が分かるか・設計書・状態・最終確認日）」「判断記録」「検証」を置く。読む人が表から必要な文書を1つ選べる状態にする。
3. 機能ごとに親ページ（機能設計書）を持つ。細かい設計は親ページからリンクする子文書に分ける。テンプレート: `FEATURE_TEMPLATE.md`。
4. 1文書1目的。文書の種類（説明・手順・リファレンス・チュートリアル）を混ぜない。複数の目的があれば分割して相互リンクする。
5. 全体設計は arc42 の章立て（目的・制約・境界・構成・実行時・データ・配置・横断事項・品質・用語）を軽くして使う。不要な章は空欄にせず「対象外」と書く。
6. 図は C4 の順（システムコンテキスト → コンテナ → 必要な箇所だけコンポーネント）。図は Mermaid でMarkdown内に書く（ローカル描画のみ。外部の描画サーバーへ設計を送らない）。図には名前と責務、線の意味を書く。
7. 重要な判断は ADR（MADR形式）を1判断1ファイルで残す。却下案と理由、日付、関連文書、置換関係を書く。古い記録は書き換えず、新しい記録で置き換える。テンプレート: `ADR_TEMPLATE.md`。
8. 設計提案は「問題・目標・非目標・提案・代替案・トレードオフ・リスク・未解決事項」を書く。実装後は現行設計とADRへ整理し、提案書を現行仕様として放置しない。

## 読んで分かりやすく書く

9. 各文書の冒頭に要約（目的・状態・最終確認日・関連文書）を置く。適用範囲と対象外を明記する。
10. 文体は「です・ます調」に統一する。主語と動作を明示し、一文には1つの判断だけを書く。略語は初出で説明し、用語は用語集に集めて表記を統一する。
11. 並列な項目は箇条書き、比較・対応関係は表にする。手順は番号付きにして、コマンド・ファイルパスは正確に書く。
12. 長くなった文書は分割して目次から辿れるようにする。行数の固定上限は設けないが、目安は1文書300行以下（未検証の運用目安。守れない場合は分割を検討する）。
13. 同じ内容を複数の場所に書かない。正本を1つ決め、他はリンクにする。

## 保守

14. 設計の変更は、コード変更と同じ作業・同じPRで設計書も更新する。最終確認日を更新し、実装とのずれは同じ作業で直す。
15. 完了前に `Check-Docs.ps1`（markdownlint・textlint・リンク検査）を通す。通らない指摘は直すか、理由を記録して除外設定に追加する。

## 完了条件

- 目次から変更対象の設計書へ辿れ、設計書の冒頭の要約・範囲・関連リンクが埋まり、リンク切れがない。
- 完了報告に、新規・更新した設計書と検査結果を書く。
